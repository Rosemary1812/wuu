# Desktop Design Notes

这份文档记录桌面端已经形成共识的设计规则。只写会反复影响多个界面的规则，不写临时想法，也不把它扩成大而全的设计系统。

## 主题与品牌气质

外观只有一根轴：`data-theme="light" | "dark"`，由持久化偏好（跟随系统/亮/暗）解析，preload 在首帧前同步 stamp 到 `<html>`。**没有第二根皮肤轴**——曾短暂存在 `data-skin`（火苗/工作双皮肤），后来判断"两者只差几个颜色时刻，不值得机制成本"，把火苗直接焊进底盘、拆掉整套 skin 机制。所以现在只有一套外观，不可选。

火苗（这套气质）的设计哲学：**底盘极素，识别度只来自少数署名时刻**。背景是中性白/黑，墨阶、发丝线、投影、几何都不带风格；不加描边、不加偏移投影、不换底色——装饰读起来是"用力"，克制读起来才是"品质"（此前的奶油底、新粗野硬影、全局墨线描边三版都因此被否）。署名时刻只有四个：

1. 空状态问候——吉祥物 + 衬线标题（`turns.css` `.empty-home-mascot` / `--empty-home-title-font`）；
2. 一个饱和 accent——landing 朱红 `--wuu-accent`（亮 `#ff3d00` / 暗 `#ff5a26`），承载发送键、侧栏活性标记、焦点环、`::selection`、链接；
3. 用户气泡的小尾角——形状细节（`.user-message` / `.chat-bubble--user` 的非对称 border-radius），不是描边；

超出这三个时刻的风格规则视为 bug。要加第四个时刻需先回答：它的完成度能不能配得上这三个。

规则：

- 所有颜色一律走 CSS custom property。亮色值写在 token 声明处（`base.css` 与各组件文件顶部），暗色覆盖只写在 `theme.css`。这两层就是全部——没有独立的 skin 文件。
- 上面四个署名时刻的值就直接住在 base/theme 与对应组件 CSS 里（accent 与 tint 是 base/theme 的 token；气泡尾角在 `turns.css`/`chat.css`；发送键朱红在 `composer.css`；`::selection` 在 `base.css`）。新增组件 token 照旧只需补 `theme.css` 暗色映射。

## 菜单

wuu 的菜单应该像轻量控件，而不是卡片或弹窗。它们服务于当前任务附近的快速选择，例如选择项目、切换模型推理档位、切换分支，或查看一句权限说明。

默认菜单规则：

- 面板使用紧凑规格：`12px` 圆角、`6px` 内边距、轻边框。
- 常规菜单项使用 `34px` 行高。
- 行间距保持 `1px`，hover 状态要轻。
- 菜单里的图标控制在 `15px` 到 `17px`。
- 宽度优先落在 `224px` 到 `300px`，只有内容确实需要时才加宽。
- 内容可能变长时设置高度上限并允许滚动，不让菜单占据大片屏幕。
- 新菜单先使用 `styles.css` 里的共享菜单变量，不要随手写一套局部数值。

不要把菜单做成卡片或对话框。重阴影、大内边距、大行高和过宽面板，会让重复使用的控件显得笨重。

## 动效

菜单动效只负责让界面有响应感，不应该抢注意力。

默认菜单进场动效：

- 时长约 `140ms`。
- 缓动使用快速 ease-out，目前是 `cubic-bezier(0.16, 1, 0.3, 1)`。
- 属性只使用 opacity、小幅 `translate3d` 和从 `0.985` 到 `1` 的轻微缩放。
- 位移距离约 `4px`，避免大幅滑动。
- 向上弹出的菜单从底边展开；向下弹出的菜单从顶边展开。

标准菜单不要使用弹跳、回弹、长淡入或逐项级联动画。这些动效会让日常控件显得过重。

内容与结构切换遵循两档节奏：

- 已加载内容之间的替换使用 `160ms`，只允许 opacity 与约 `4px` 的 `translate3d`；会话、设置页和工具 Tab 共用这套节奏。
- 侧栏这类会改变可用空间的结构过渡使用 `240ms`。过渡期间暂停消息流的重复尺寸测量和滚动校正，结束后统一对齐一次，避免动画每帧触发主线程布局工作。

点击结果必须立即进入目标状态，动画只解释状态变化，不能把数据切换或可操作状态推迟到动画结束之后。

## 减弱动效

所有共享动效都必须尊重 `prefers-reduced-motion: reduce`。

菜单在减弱动效模式下直接关闭进场动画。以后新增控件动效时，也应该在同一个媒体查询下关闭动画，或改成即时状态变化。

## 新增弹出层

新增 dropdown、menu 或小 popover 时：

1. 先复用现有菜单变量和菜单进场动画。
2. 选择能保证文字可读的最窄宽度。
3. 根据实际弹出方向设置 `transform-origin`。
4. 内容会增长时加高度上限。
5. 只有当界面职责不同，例如 dialog、inspector 或常驻侧栏，才新建另一套视觉规格。

## 消息流节奏

消息流的空白是一套固定用途的节奏。相邻元素要么靠近表达"同组"，要么留出明确边界；不要把多个局部间距叠成无法解释的死空间（历史教训：不可见但占位的 hover 操作行曾把 turn 边界撑到 60px）。

当前阶梯（token 声明在 `conversation-shell.css`，边界值在 `turns.css`；14px 正文下实机校过一轮，更小的一版被判过密）：

- 段内：行高 `1.75`（正文 prose 测度已限制在消息最大宽度内）。
- 工具行之间：`9px`（`--conversation-activity-gap`）；commentary 紧跟它引出的工具组时也收到 `9px`。
- 块之间：`18px`（段落、fold 内条目、answer 内块共用 `--conversation-prose-block-gap` / `--conversation-message-element-gap`），对行内空隙约 1.7 倍——低于这个比例段落就不成块。
- 结构交接：`16px`（发丝线 → process、process 折叠行 → 最终答案）。
- 节标题上方：块间距 + `12px`（`.rich-heading`）。
- 问 → 答：`24px` + 发丝线 + `16px`（发丝线负责解释这段空白）。
- turn 边界：`24px` 干净空白（`.turn` margin-bottom）。

配套规则：

- hover 操作行一律 overlay，不占流内空间；只有最新一条答案的常驻操作行例外（真实可见才配占位）。overlay 画进 turn 边界带，`.turn:hover/:focus-within` 时解除 `content-visibility` 的 paint containment（详见 `turns.css` 注释）。
- 正文层级停在"低语"级：标题 = 同字号 semibold + 上方额外空间（单一层级，不还原 h1-h6 字号）；`**bold**` = `--weight-medium`。要么全平（灰墙、无锚点），要么字号跳变（文档感、太吵），都被否过。
- 答案 prose、reasoning 与用户气泡共用一把测度尺（`--conversation-message-max-width`）；工具行和卡片仍然可以占满内容列。
- 过程区在只有 commentary、reasoning 或工具活动时保持展开，标题使用“正在处理”。第一段非空且确认的 `final_answer` 到达时立即进入回答交接：过程详情收成一行、旧过程预览不再重复显示，标题改为“正在回复”，最终答案开始占据主阅读位置。turn 完成时只把这一行改成“用时 …”，不再发生第二次收缩。
- 用户在回答交接后手动展开过程区时，本轮保持展开；自动状态变化不得抢回控制权。失败、中止或没有 `final_answer` 的 turn 不触发回答交接。

## 排队消息

排队消息（queue）和引导消息（guide）是 composer 的内部内容，不要在外面另起卡片。

默认规则：

- 队列直接放在 `.composer-shell` 内部、attachment strip 之上，宽度自然等于输入框。
- 每条占满壳子宽度，行间用 `1px` hairline 分隔，**不要**用大圆角、阴影或独立背景。
- 行内最多 3 个区域：位置序号、预览文本（单行截断）、动作区。动作区只保留两个按钮：删除（`X`）和 `…` 菜单。删除按钮常驻，菜单按钮可隐藏到 hover/focus-within。
- 序号用 `11px` 以下的 dim 灰、`tabular-nums`，不要做成 badge 或 dot。
- guide 状态不要用单独的图标行——用 row 文字色变化（`--turn-warning-text`）表达"已经是引导"即可。
- 行 hover 用 `rgba(31, 35, 40, 0.035)` 这种低于 5% 的浅灰，不要换背景色。
- 队列本身已经是计数，**不要**再在 toolbar 上重复"已排队 N 条"这种 badge。
- 队列容量是异常情况，先不限制高度；超长时再考虑加 `max-height + 内部滚动`，不要默认就滚动。
