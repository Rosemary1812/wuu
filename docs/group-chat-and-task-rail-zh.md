# wuu 群聊与任务板：机制全解

写作时间：2026-07-06。三份设计文档（`docs/plans/2026-07-03-resident-named-agents.md`、
`docs/plans/2026-07-03-chat-style-threads-design.md`、
`docs/plans/2026-07-06-agent-task-rail-design.md`）记录的是**决策与理由**，
读起来是补丁摞补丁；这一篇记录的是**现在它究竟怎么工作**——把散在三份文档
和代码注释里的机制串成一条线。如果两边冲突，以设计文档为准，然后回来修这篇。

读者假定：你用过 wuu 的群聊，想搞明白「为什么 agent 有时候不说话」「任务卡
是怎么流转的」「哪些事有按钮、哪些事要开口说」。

## 一、登场角色

**用户**就是你。你在界面上说话、点按钮，是所有权威的最终来源。

**常驻具名 agent**（named agent）是这套系统的主角。每个具名 agent 是一个
持续存在的身份：一个大脑、一段连续的会话、一本自己的记忆笔记本。它不是
「每条消息起一个新实例」——你上周跟它说过的话、它自己记下的教训，都还在。
它有名字、角色、一句话简介，住在自己的家目录里。具名 agent 可以被拉进
多个群，但所有消息最终都汇入它唯一的大脑里处理。

**匿名 worker** 是干粗活的：具名 agent 觉得某件事又重又能并行，就派几个
匿名 worker 去跑。worker 是纯执行体，干完即散，不能发言、不能再派人。
编排权永远留在具名 agent 的大脑里。

**群**是一个聊天房间：显式的成员表（谁在群里是一张名单，不是隐式规则）、
一条主流（main stream）、若干挂在消息下面的子线程。群的规模有上限——这不
是产品限制，是扇出宽度的物理约束：主流里每条消息都会唤醒每个成员推理一次。

## 二、一条消息的旅程

你在群里发一句话，接下来发生的事：

1. **投递。** 系统给群里每个成员（除了发话者自己）各推一个「信封」。信封
   里只有这一条消息，外加几个属性：来自哪个线程、谁说的、有没有点名你
   （@你 或 DM 就算点名）、这条消息经过了几跳 agent 接力（跳数越高，说明
   话题离用户越远、越接近 agent 之间的自嗨，越可以不接茬）。
2. **唤醒。** 收到信封的 agent 被「踢」醒，跑一个回合来处理它。如果它正忙
   （比如在执行一个任务），信封不会丢，排在它的收件箱里，等它空下来自动
   送达。如果积了好几条，一次性合批塞给它，让它通读完再决定怎么反应。
3. **决定要不要说话。** 这是新人最容易误解的一环：**沉默是缺省，也是合规
   的回应**。契约只有两条硬规则——用户的 DM 和 @点名必须回应（回答，或者
   明确说不接）；其他一切默认沉默。每条消息处理完会自动落一个已读回执，
   所以「我看过了」不需要说出来，界面上本来就能看到。agent 之间的 @点名
   可以用一个表情回应（react）抵扣，不必开口。
4. **如果说话。** 一个回合最多发一贴。发出来的话是给人读的：不准复述别人
   说过的话、不准报幕自己的动作（「已收到」「我先待命」都是违规）、不准
   出现内部标识符、跟着用户的语言走。

为什么这么苛刻？因为第一次实弹演练（三个 agent 修一个一行的 bug）主流刷了
29 条消息，其中约 15 条是纯协调噪音。事后复盘的结论是：**这不是提示词写得
不够狠，而是协调状态没有自己的数据结构，只能被「说」出来**。于是有了任务板。

## 三、任务板：工作跑在卡上，不跑在聊天里

参照系是 Raft（一个多 agent 协作系统）的经验：执行要尽快收敛成
「一个 owner + 一个线程 + 一个状态」。落到 wuu：

**谁做什么，看板不看聊天。** 有活要干，第一步是把活变成板上的一张卡
（任务卡），或者认领板上已有的卡。认领是原子的抢占：两个 agent 同时伸手，
只有一个成功，输的那个直接走开——不回复、不解释、不「我来帮忙看看」。
聊天里于是不再出现认领竞赛。

**过程进任务线程，主流只留结论。** 每张卡自带一条子线程。干活期间的进度、
问题、中间产物，都发在卡的线程里，只推送给关注这张卡的人（弱隔离：其他
群成员不被打扰，但想看随时能翻）。例行进度连发都不用发——卡的状态本身就
说明「有人在干」。主流最终只该剩两样东西：开工时的一句交代，和每张卡收尾
时冒泡上来的一句结论。

**状态是字段，不是话。** 卡的一生：

- **出生。** 三种方式：agent 直接建卡（可以锚在某条消息上，也可以独立
  存在——拆活给队友抢时通常是独立卡）；一段讨论聊成熟了，agent 把讨论串
  原地升级成卡；或者人在界面上点「升级为 Task」。agent 建的卡默认**无主**
  （born-open）——建卡的人是派活的，不是干活的；要自己干就在建卡时顺手
  自认领。
- **认领。** 抢到卡的 agent 成为 owner，承担唯一责任：干活、汇报、交卡。
  注意 owner 不是 lead——认领只给你干活的责任，不给你指挥别人的权力。
  指挥权（workflow 编排）是另一条线，只能由人在升级时显式授予某个成员。
- **干活。** 在卡的线程里进行。需要帮手就拆子卡让别人抢，而不是在聊天里
  发号施令。
- **报结果。** 干完并验证过，owner 把卡置为**待验收**，附一句话结论
  （结果 + 怎么验证的）。这一笔就是汇报本身，不需要再发一条消息说「我做
  完了」。验收别人的活也是同样的规矩：验收本身是工作，先认领对应的卡，
  验收报告发卡的线程，结论走卡的状态——不进主流（这一句是 2026-07-06 深夜
  补进契约的，起因见下一章）。
- **验收与销卡。** 配置项 `task_review` 决定谁把关：`human`（默认）模式下，
  卡停在待验收，等人确认后把结论冒泡回主流、卡变已解决；`auto` 模式下
  agent 报结果的瞬间自动冒泡销卡，适合「我就不盯着了」的全自主运行。

这套东西上线后的 A/B 对比：同类问题，主流从 29 条降到 5 条，协调噪音归零，
三张卡三个不同的 owner，没有重复劳动，也没有干完活以后的寒暄尾巴。

## 四、无主的卡会喊人（2026-07-06 深夜补上的一环）

任务板第一版有个隐蔽的洞：**建卡这个动作本身不出声**。卡写进了库、界面上
的面板刷新了，但没有任何 agent 因此被唤醒。第二次实弹里三个 agent 恰好都
在回合里，看见了板上的新卡；可如果建卡时大家都闲着，一张无主的卡会永远
挂在板上——没有任何机制会再提起它。实弹里确实留下了一张这样的卡：一张
验收总卡（伞任务）从升级那刻起就无主，代表的活干完了，卡还挂着。

修法是给「无主」这个状态装一个喊人的机制。卡在板上进入无主状态的每个时刻
——建卡没认领、讨论升级成卡没认领、owner 把卡放回板上——系统会给群里其他
成员每人发一条系统信封，内容大意是：「某某把一张什么卡放上板了，没人认领。
是你的活就领走；不是，或者没抢到，就安静结束回合。」这条信封走的是普通
消息同一条投递管道，所以「建卡时没人在场」也不怕：信封排在各自收件箱里，
谁先空下来谁先看到。它不点名任何人、不产生已读回执、不要求回应——认不认领
仍然是每个 agent 自己的判断，喊人机制只保证「板上有活」这个事实一定会到达
每个人的耳朵里。自认领的卡不喊——没有别人需要做的事。

## 五、人的位置：哪些事有按钮，哪些事靠说话

人介入这套系统有两条路：点按钮，或者在群里说话驱动 agent。

**界面上现有的按钮**（消息下面的子线程面板里）：

- 在一条消息上开讨论串；
- 「升级为 Task」——把讨论串升级成任务卡，同时可以指定一位成员当 lead
  （这是唯一授予编排权的入口）；
- 「完成 Task」——人写一句结论，冒泡回主流并销卡（`task_review: human`
  模式下的验收动作就是它）。

**说话能驱动的**：全部。建卡（含独立卡）、认领、放手、升级、报结果、
退订、问板上有什么——你在群里说一句「把这个整理成任务放板上，别自己
认领」，agent 就会替你做，这条路是完整闭环（2026-07-06 实弹验证过）。

## 六、已知的裂缝（2026-07-06 盘点）

诚实清单。以下四条都是**桌面前端的欠账**——服务端数据和 agent 侧机制都是
好的，界面没接住。设计文档当时明确把「任务看板页」列为后续工作，这四条就
是那个后续工作的具体内容：

1. **独立卡在界面上不可见。** 界面渲染任务卡的唯一入口是「挂在某条消息
   下面的牌子」；没有锚点消息的独立卡（恰恰是拆活的主力形态）在界面上
   没有任何挂靠点，被前端直接丢弃。人要想知道板上有哪些独立卡，目前只能
   开口问 agent。
2. **「待验收」不上屏。** 默认模式下人是验收环节的把关者，但前端不认识
   「待验收」这个状态——agent 报完结果，卡在界面上和干活中的卡长得一模
   一样，没有任何「等你验收」的信号。「完成 Task」按钮在，但没人引导你
   去点。
3. **owner 不上屏。** 谁认领了卡、卡有没有人管，服务端每次都发，前端的
   协议类型里压根没有这个字段。上一张伞任务卡悬空多日没人发现，直接原因
   就是它。
4. **人不能直接建卡。** 人建任务只能走「先开讨论串、再升级」两步；想直接
   往板上扔一张卡，得开口让 agent 建。

修复方向（按投入从小到大）：前端协议补上「待验收」状态和 owner 字段，任务
卡渲染 owner 头像和待验收标识；给独立卡一个展示位（或直接做看板页）；
面板上加一个人建卡的入口。
